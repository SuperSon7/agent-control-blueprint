# [portfolio] 중복 실행 방지

mode: portfolio

- 공부할 것: at-least-once 전달, idempotency key, unique constraint, inbox/outbox, 동시 요청, 로컬 트랜잭션과 외부 부작용의 경계.
- 네가 결정할 것: 동일 요청의 기준, 같은 내용의 새 요청과 재전송의 차이, 키 범위·보관 기간, DB 기록과 수신 offset 순서.
- 먼저 직접 만들 것: 요청 식별자와 트랜잭션 경계. job 생성, inbox 접수, 수신 확인이 어디에서 연결되는지 도식화한다.
- 비교할 선택지: 메모리 set, 사전 조회 후 insert, unique constraint와 트랜잭션.
- 네가 고를 실험: 동일 update 100회 순차 전달, 같은 키 동시 전달, insert 사이 종료, 외부 게시 성공 후 응답 유실, 동일 내용이지만 다른 요청 ID.
- 네가 해석할 것: 생성된 job 수, 외부 부작용 수, 중복 알림, 새 요청이 잘못 억제되는지.
- 실제 완료 근거: 같은 수신 이벤트가 하나의 job에만 연결, 새 요청은 정상 접수, 외부 결과 불명은 조회·대조, outbox 전송의 중복 가능성을 정직하게 기록.
- 설명 질문: DB의 unique constraint만으로 PR 생성까지 정확히 한 번을 보장할 수 있는가? 전달 보장과 실행 보장은 어떻게 다른가?

소유자 체크포인트: 설계 결정 → 실험 해석 → 핵심 설명.

현재 상태: 제안. 실제 구현·실험·학습 결과는 아직 없다.
